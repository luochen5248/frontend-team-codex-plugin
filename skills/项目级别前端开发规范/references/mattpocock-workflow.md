# Matt Pocock 方法论（智慧检测大屏系统适配版）

> 融合自 Matt Pocock Skills (Kimi) 的 6 个子技能。原技能为通用方法论，此处结合本项目实际（Vue 3.2.47 + Cesium、无自动化测试框架、验证靠用户本地 `npm run dev`、项目工作日志体系）做落地适配。

---

## 1. Grilling — 需求对齐

> 核心理念：**没有人一开始就知道自己想要什么。** 软件开发最常见的失败模式是沟通偏差。

### 触发
"对齐一下需求"、"帮我理清这个"、"想清楚再动手"、"讨论一下设计"、"确认一下方案"、"stress-test"、"grill"、"plan"、"design"、"方案"、"需求"、"计划"、"思路"

### 工作方式

1. **逐分支遍历决策树**：一次只问一个问题，等用户回答后再继续。**禁止一次抛多个问题**（会让人困惑）。
2. **每个问题提供推荐答案**：先说「我建议 X，因为 Y」，再等用户确认或调整。推荐答案是展示理解方向，不是替用户决定。
3. **能用代码回答的，用代码回答**：例如「这个功能是否已实现？」→ 直接搜索代码，不麻烦用户。

### 完成标准
决策树所有分支已解析，无未解决依赖。**不要急于结束**——如果心中还有「这里可能还要确认」，继续问。

### 本项目适配
- 需求含糊（"优化一下/弄好/看着办"）、描述 < 20 字无上下文、或多个决策分支时，强制进入本流程。
- 本项目有大量既有约定（见 project-conventions.md），对齐时**先查规范再问**，能由规范/代码回答的问题不问用户。

## 2. Grill-with-Docs — 有代码库的对齐

### 触发
grilling 的所有场景 + "在这个项目里"、"在代码里"、"当前目录"、"这个项目"、"代码库"

### 与纯 grilling 的区别
| | grilling | grill-with-docs |
|---|---|---|
| 代码库 | 无 | 有 |
| 保存文件 | 否 | 是（CONTEXT.md + ADR） |
| 使用场景 | 任何计划/设计 | 代码库上的计划/设计 |

### 工作方式

1. 检测代码库：存在 `package.json` / `src/` / `.git/` 即判定有代码库。
2. 运行 grilling 面试循环（一次一问 + 推荐答案）。
3. **对话中产生的术语决策，立即写入 CONTEXT.md**——不要等会话结束，不要批量，当场写。
4. 需要记录的架构决策（难逆转 / 没有上下文会惊讶 / 有真实权衡）→ 询问用户后创建 ADR 到 `docs/adr/000X-xxx.md`。
5. 与代码交叉验证：用户描述行为时检查代码是否一致，发现矛盾指出并确认哪个是对的。

### 本项目适配
- 本项目的 CONTEXT.md 角色由 **《开发注意事项.md》** 承担：对齐过程中产生的新约定/新术语/新决策，同步追加到对应章节（或项目工作日志），不必另建 CONTEXT.md。
- ADR 可简化为《开发注意事项.md》中「遗留事项/待办」或新增「决策记录」小节，避免过度文档化。

## 3. TDD — 测试驱动开发（垂直切片）

> 核心原则：**测试应该验证行为，而不是实现。** 内部实现可以全改，测试不应该崩。

### 触发
"写测试"、"测试先行"、"TDD"、"红绿重构"、"red-green-refactor"、"先写测试"、"写功能"、"实现"、"开发"、"测试"、"test-first"、"unit test"、"integration test"

### 反模式：水平切片（绝对禁止）
```
WRONG (水平):
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5
```
批量写的测试验证的是**想象的行为**，最终测试的是**形状**（数据结构/函数签名），不是用户可见的行为。

### 正确方式：垂直切片（Tracer Bullets）
```
RIGHT (垂直):
  RED→GREEN: test1→impl1   （一个行为：写测试→失败→写最少代码→通过）
  RED→GREEN: test2→impl2
  ...
```
每个测试回应上一个循环学到的东西。规则：
- 一次一个测试；只写当前测试通过所需的最少代码；不要预测未来的测试
- 测试聚焦**可观察行为**；**RED 时绝不重构**，先变绿
- 重构阶段：提取重复 → 深化模块 → 每次重构后跑测试

### 每循环检查清单
```
[ ] 测试描述行为，不是实现
[ ] 测试只使用公共接口
[ ] 测试在内部重构后能存活
[ ] 代码是当前测试所需的最少
[ ] 没有添加推测性功能
```

### 本项目适配
- **项目当前无自动化测试框架**（package.json 无 jest/vitest），因此：
  - 「测试」落地为**静态自查 + 用户本地运行验证**：每完成一个垂直切片，做一次语法/类型自查，交用户 `npm run dev` 验证，通过再进下一个切片。
  - 若后续引入 vitest（与 Vite 同生态），本流程即可无缝升级为真实 RED→GREEN 循环。
- 垂直切片思想在**无测试场景同样适用**：复杂页面/功能拆成「一个面板 → 一个交互 → 一个图表」逐块交付验证，禁止一次性堆完所有功能。

## 4. Diagnosing Bugs — Bug 诊断六阶段

> 核心原则：**Phase 1 就是这个 skill。** 没有 tight feedback loop（紧反馈循环），再多的 staring at code 也救不了你。

### 触发
"修 Bug"、"跑不通"、"报错"、"抛异常"、"性能慢"、"卡顿"、"慢查询"、"debug"、"diagnose"、"排查"、"定位问题"、"故障"、"崩溃"、"fail"、"broken"、"throwing"、"性能回归"、"内存泄漏"、"race condition"

### 六阶段

**Phase 1 — Build a feedback loop（建立反馈循环）【最重要，投入不成比例的努力】**
目标：一个 tight 的 pass/fail 信号——一个命令/操作，运行后能告诉你「bug 还在」（red）或「已修复」（green）。

尝试顺序（从易到难）：
1. Failing test → 2. Curl/HTTP 脚本 → 3. CLI 调用对比输出 → 4. Headless browser（Playwright 断言 DOM/console/network）→ 5. 重放捕获 trace → 6. Throwaway harness（最小系统子集）→ 7. Property/fuzz → 8. Bisection（git bisect run）→ 9. Differential loop（新旧版对比）→ 10. HITL 脚本

**收紧循环**：更快？（跳过无关初始化）信号更尖锐？（断言具体症状，不是"没崩溃"）更确定？（固定时间/种子/冻结网络）

**非确定性 Bug**：目标不是 clean repro，而是**提高复现率**（循环 100 次、并行化、加 stress、注入 sleep）。50% 的 flaky bug 可调试，1% 不是。

**实在建不出循环**：停下来明确说，列尝试过什么，向用户要 (a) 复现环境访问 (b) 捕获的 artifacts（HAR/日志/core dump/录屏）(c) 临时监控权限。**没有 tight loop 不要进入 Phase 2。**

**Phase 2 — Reproduce + minimise（复现 + 最小化）**
- Loop 跑 red，确认失败模式是用户描述的（不是附近另一个失败）
- 捕获精确症状（错误消息、输出、耗时）
- **minimise**：逐个砍掉输入/调用者/配置/数据/步骤，每次砍后重跑 loop，只保留 load-bearing 元素。完成标准：每个剩余元素都是 load-bearing（砍掉任何一个都会变绿）。

**Phase 3 — Hypothesise（假设）**
- 生成 **3-5 个 ranked hypotheses**（单一假设会锚定第一个看似合理的想法）
- 每个假设**可证伪**："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让 bug 更糟"。说不出预测的假设是 vibe，丢弃或锐化。
- **给用户看 ranked list 再测试**——用户常有能瞬间重排的知识（"我们刚部署了 #3 的改动"）。

**Phase 4 — Instrument（探测）**
- 每个 probe 必须映射到 Phase 3 的某个预测；**一次只改变一个变量**
- 工具优先级：Debugger/REPL > Targeted logs > **绝不 "log everything and grep"**
- 调试日志加唯一前缀 `[DEBUG-xxxx]`，清理时 grep 一次性删除
- 性能回归：log 通常是错的，先建 baseline 测量再 bisect。**先测量，再修复。**

**Phase 5 — Fix + regression test（修复 + 回归测试）**
- 修复**之前**写回归测试——但**只有**在存在 correct seam（测试在真实调用点 exercising 真实 bug 模式）时
- 没有 correct seam 本身就是发现：架构阻止了 bug 被锁定，标记给下一阶段
- 流程：最小复现 → 该 seam 的 failing test → 看它失败 → 应用修复 → 看它通过 → 重跑 Phase 1 原始 loop

**Phase 6 — Cleanup + post-mortem（清理 + 复盘）**
- [ ] 原始复现不再复现（重跑 Phase 1 loop）
- [ ] 回归测试通过（或缺少 seam 已记录）
- [ ] 所有 `[DEBUG-...]` 已移除
- [ ] 临时原型已删除
- [ ] 正确的假设写在 commit/PR message 中

然后问：**什么能阻止这个 bug？** 若答案是架构变更 → 转交重构。**修复后再提建议，不是之前。**

### 本项目适配
- 项目验证靠用户本地，因此 Phase 1 的 loop 通常落地为：「让用户复现 + 描述现象 → 我给出复现脚本/检查点 → 用户反馈」的迭代循环；或利用 dev server + 浏览器 console 检查。
- 本项目既有踩坑表（project-conventions.md 第 10 节）是**现成的假设库**：遇到新 Bug 先对照踩坑表排查（ECharts v-if 切换、mapcardNew 高度链、grid 布局错位、viewer 属性不刷新等），命中即省去 Phase 3。
- 调试日志唯一前缀约定同样适用于页面 console.log（`[DEBUG-xxx]`）。

## 5. Handoff — 跨会话交接

### 触发
"会话太长了"、"换一个新会话"、"交接一下"、"handoff"、"上下文满了"、"新开一个对话"、"分几步做"、"多会话"；会话 token 接近上限时

### 核心原则
**不要丢掉已完成的思考。** 交接文档的价值：让新会话**不重新问一遍已经问过的问题**。

### 工作方式

1. 提取关键信息：已完成决策 / 未完成待办（含缺什么信息）/ 关键约束 / 已发现的坑 / 相关文件路径
2. **不重复已有内容**：PRD/ADR/Issue/代码 diff 只引用路径或编号，交接文档只补充**会话中产生但尚未写入任何文件**的信息
3. 文档末尾加 **Suggested Skills** 部分推荐下一步技能
4. 脱敏：API key、token、密码、PII、内部机密一律不写入
5. 保存到当前 workspace（**不存 temp 目录**）：`<workspace>/handoff-<timestamp>.md`，如 `handoff-20260815-0720.md`
6. 告知用户文件路径

### 文档模板

```markdown
# Handoff — <简短主题>

## 会话背景
<当前在做什么，为什么交接>

## 已完成决策
- <决策 1：结论>
- <决策 2：结论>

## 未完成待办
- <待办 1：需要什么信息>
- <待办 2：需要什么信息>

## 关键约束
- <约束 1>

## 已知风险/已排除选项
- <坑 1>

## 相关文件
- 规范: `开发注意事项.md`
- 代码: `src/views/<板块>/<板块>.vue`
- 记忆: `memory/YYYY-MM-DD.md`

## Suggested Skills
- `frontend-team` — 继续本项目开发
- `<子方法论>` — 如下一会话是 Bug 修复走六阶段诊断
```

### 本项目适配
- 与项目工作日志体系互补：日志记规范/踩坑（长期价值），handoff 记**会话中间态**（当前进度、待办、未写入文件的决策）。
- 长任务（如大板块开发）建议在完成一个里程碑后主动提醒用户是否生成 handoff。

## 6. To PRD — 对话转 PRD

### 触发
"写 PRD"、"出需求文档"、"整理需求"、"写成文档"、"to-prd"、"PRD"、"需求文档"、"产品需求"、"功能文档"、"spec"、"写成 spec"、"记下来"、"形成文档"

### 核心原则
**PRD 是供需双方对齐后的契约。** 它不是新信息，而是把会话中已讨论的内容**结构化、完整化**。

### 工作方式

1. 探索代码库（若未做）：当前结构、相关模块 seams、已有 PRD/spec
2. 确定测试 seams：优先现有 seams，用最高层 seam（越少越好），与用户确认
3. 用项目领域术语撰写 PRD（模板见下）
4. 发布到 Issue Tracker（GitHub MCP/Token/CLI/本地 Markdown）；失败回退本地 markdown

### PRD 模板

```markdown
## Problem Statement
用户面临的问题，从用户视角描述。

## Solution
解决方案，从用户视角描述。

## User Stories
1. 作为一个 <角色>，我想要 <功能>，以便 <收益>
2. ...

## Implementation Decisions
- 将构建/修改的模块
- 模块的接口变化
- 技术澄清
- 架构决策
- Schema 变化
- API 契约
- 具体交互
（不包含具体文件路径或代码片段——这些会过时；原型产出的状态机/schema/类型形状可 inline 并标注来自原型）

## Testing Decisions
- 什么是好测试（只测外部行为，不测实现细节）
- 哪些模块将测试
- 测试的参考

## Out of Scope
本 PRD 不包含的内容。

## Further Notes
任何其他备注。
```

### 本项目适配
- **无 Issue Tracker 配置**：默认回退本地 markdown，保存到 `资料/` 或工作区（如 `资料/prd/<feature>-PRD.md`）。
- 撰写时术语/板块名用本项目领域词（路基/路面/桥梁/隧道/地下、板块/模块、`--color-*` 变量、CesiumMap 等）。
- 与 grilling 联动：**对齐完成后**再写 PRD，不要边问边写。

## 典型工作流串联（本项目）

```
需求阶段   grilling / grill-with-docs → 对齐需求，确认设计（更新《开发注意事项.md》）
文档阶段   to-prd → 需求对齐后沉淀 PRD（本地 markdown 回退）
开发阶段   tdd 垂直切片 → 一次一个面板/交互/图表，逐块交付用户验证
调试阶段   diagnosing-bugs → 六阶段诊断（先对照踩坑表，再建反馈循环）
交接阶段   handoff → 长会话压缩上下文，跨会话接力（配合项目工作日志）
```
